## Plan

### Decision needed: where IDs come from
DATA_MODEL says "uuid v7, generated in the app". Postgres 18 now has a native `uuidv7()`.

| Option | Trade-off |
|---|---|
| **A. App generates (`uuid` package v7), with DB default `uuidv7()` as a fallback** *(recommended)* | The domain can create an entity with its ID before saving it (DDD aggregates, linking IDs in one transaction, deterministic IDs in tests). The DB default only covers rows inserted by hand (psql, ad-hoc SQL), and both sources produce v7, so ordering stays consistent. `uuid@14.0.3` has zero dependencies and is the standard implementation. |
| B. DB only (`default uuidv7()`, read back with `returning`) | No package, one source. But entities get their ID only after the insert, which makes domain code and tests awkward. |
| C. App only, no DB default | Like A, but hand-written SQL must always supply IDs. |

The rest of the plan assumes **A**. `shared/ids.ts` exports `newId(): string` (v7) for the domain, so the domain doesn't import the package directly.

### Tables (`apps/api/src/modules/identity/infrastructure/schema.ts`)
This follows DATA_MODEL §3 "identity", with the details below filled in.

**Postgres enum `role`** is built from `Role.options` in contracts (`admin`, `mentor`, `program_manager`). The contracts package stays the single source.

**`users`**
| Column | Type | Constraints / default |
|---|---|---|
| id | uuid | PK, default `uuidv7()` |
| email | **citext** | not null, **unique**. citext makes `A@x.com` and `a@x.com` the same at the DB level. The app still trims and lower-cases on input (3.2). |
| name | text | not null |
| google_sub | text | null, **unique**. Filled on first Google sign-in. Postgres allows many NULLs under a unique constraint. |
| avatar_url | text | null |
| is_active | boolean | not null, default `true` |
| last_login_at | timestamptz | null |
| created_at | timestamptz | not null, default `now()` |
| updated_at | timestamptz | not null, default `now()`. The app sets it on update (Drizzle `$onUpdate`). There's no trigger, because all writes go through repositories. |

**`user_roles`**
| Column | Type | Constraints |
|---|---|---|
| user_id | uuid | FK → users `on delete cascade` |
| role | `role` | not null |
| granted_by | uuid | FK → users, **nullable** (see below) |
| granted_at | timestamptz | not null, default `now()` |
| | | **PK (`user_id`, `role`)** |

**`sessions`**
| Column | Type | Constraints |
|---|---|---|
| id | text | PK: SHA-256 hex of the token. The raw token is only ever in the cookie. |
| user_id | uuid | FK → users `on delete cascade`, **indexed** (to revoke all of a user's sessions) |
| expires_at | timestamptz | not null, **indexed** (to clean up expired sessions) |
| user_agent / ip | text | null |
| created_at | timestamptz | not null, default `now()` |

### Two small changes to DATA_MODEL
1. **`user_roles.granted_by` is nullable.** The first admin, created by the bootstrap seed in 3.4, has no one to grant the role. `NULL` means "granted by the system (bootstrap)". Every other grant records the admin who made it.
2. **`users.email` is `citext`**, as decided in 1.5, rather than "text, lower-cased". The DB enforces case-insensitive uniqueness, even for rows written outside the app.

### Deletes
**Users are never deleted.** Deactivation is `is_active = false`, which keeps feedback attributable.
- The cascades on `user_roles` and `sessions` exist only so that a test or a manual cleanup can remove a user cleanly.
- Every other foreign key to `users` in later tables will be `restrict`, so feedback can never lose its author.

### Tests
- **Unit (`ids.test.ts`):** `newId()` returns a valid UUID with version 7, and IDs generated in sequence sort in creation order.
- **Integration (`schema.int.test.ts`, using the 1.6 harness, so each file gets its own migrated database):**
  - A user inserted with only email and name gets a v7 `id` from the DB default, `is_active = true`, and `created_at`/`updated_at` set. An app-supplied `newId()` is kept as given.
  - A second user with `A@Example.com` after `a@example.com` is rejected with a unique violation (`23505`).
  - Duplicate `google_sub` is rejected. Two users with `google_sub = NULL` are fine.
  - Granting the same role twice is rejected (PK). An invalid role value is rejected (`22P02`). `granted_by = NULL` is allowed.
  - A session for an unknown user is rejected (FK `23503`).
  - Deleting a user removes their roles and sessions (cascade).
